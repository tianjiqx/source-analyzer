# SKILL 04 - 上下文管理分析

> **核心问题**: Token 预算如何分配？Skill 如何按需加载？上下文如何压缩和隔离？

## 1. 上下文预算模型

### 1.1 Token 预算分配

```
典型的上下文窗口分配:
┌────────────────────────────────────────┤
│ 系统指令 (System Prompt)     ~10%      │
├────────────────────────────────────────┤
│ Skill 元数据列表 (发现层)    ~1-3%     │
├────────────────────────────────────────┤
│ 活跃 Skill 全文 (加载层)     ~10-30%   │
├────────────────────────────────────────┤
│ 对话历史                     ~20-40%   │
├────────────────────────────────────────┤
│ 工具输出 / 代码 / 文件       ~20-40%   │
├────────────────────────────────────────┤
│ 剩余生成空间                 ~10-20%   │
└────────────────────────────────────────┘
```

### 1.2 预算约束策略

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **元数据预算** | 所有 Skill 元数据总和 < N% 窗口 | Skill 数量多的项目 |
| **单 Skill 预算** | 单个 SKILL.md < N tokens | 控制单 Skill 加载成本 |
| **深度限制** | references/ 文档递归深度限制 | 参考文档多的项目 |
| **压缩触发** | 上下文使用超过阈值时触发压缩 | 长会话场景 |
| **历史裁剪** | 老旧消息/工具输出自动裁剪 | 多轮对话 |

## 2. 加载策略

### 2.1 延迟加载 (Lazy Loading)

```
检查要点:
- 元数据何时进入上下文？（启动时 / 首次提及）
- 完整 SKILL.md 何时加载？（匹配后 / 引用时）
- references/ 文档是否递归加载？
- 是否有 "渐进披露" 机制？
```

### 2.2 内联 vs 隔离执行

| 模式 | 描述 | 优势 | 劣势 |
|------|------|------|------|
| **内联执行** | Skill 在主对话上下文中执行 | 共享上下文，简单 | 消耗主窗口 Token |
| **隔离执行** | Skill 在子代理 fork 中执行 | Token 隔离，可并行 | 上下文传递开销 |
| **混合模式** | 轻量内联 + 重量隔离 | 平衡效率与隔离 | 需要路由决策 |

### 2.3 上下文工程四操作

```
检查项目是否实现以下操作:

SELECT  — 按需选择哪些信息进入上下文
WRITE   — 将发现写回文件系统，释放上下文
COMPRESS — 将冗长上下文压缩为摘要
ISOLATE  — 将大任务隔离到子代理
```

## 3. 核心分析问题清单

- [ ] Skill 发现层占用多少 Token？是否在合理范围（< 3%）？
- [ ] 单个 Skill 加载后占用多少 Token？是否有大小限制？
- [ ] 是否实现了延迟加载？元数据 vs 完整内容的边界在哪？
- [ ] 长会话时上下文如何管理？有无压缩/裁剪机制？
- [ ] 是否支持隔离执行？子代理如何与主代理通信？
- [ ] 参考文档（references/）如何加载？是否递归？
- [ ] 上下文溢出时的降级策略是什么？

## 4. Golden Rules 提炼

### 常见可移植原则

- **发现层极简**: Skill 元数据必须压缩到窗口的 1-3%
- **按需加载**: 完整内容只在激活时加载，不预加载
- **文件作为记忆**: 将发现写入文件，而非保存在对话历史中
- **隔离重活**: 大 Token 消耗的任务 fork 到子代理
- **渐进披露**: 先摘要 → 按需展开 → 深入细节

## 5. Gotchas

### 典型陷阱

- **元数据膨胀**: Skill 越来越多，元数据列表超出预算被截断
- **引用链爆炸**: Skill A 引用 reference B，B 引用 C，递归加载
- **隔离后失忆**: 子代理执行完丢失主代理上下文，需要重新解释
- **压缩丢信息**: 自动压缩可能删除关键决策记录
- **历史堆积**: 多轮对话 + 大量工具输出 → 窗口耗尽
- **隐性 Token 成本**: frontmatter / 格式化字符的 Token 开销

## 6. 量化评估

| 指标 | 计算方法 | 目标值 |
|------|----------|--------|
| 发现层占比 | 元数据 Token / 窗口大小 | < 3% |
| 单 Skill 大小 | SKILL.md Token 数 | < 2000 tokens |
| 加载延迟 | 从触发到完整加载的步骤数 | ≤ 2 步 |
| 隔离能力 | 是否支持 fork 执行 | 有/无 |
| 压缩机制 | 是否有上下文压缩 | 有/无 |

# 初步分析产出规格

在 `00-initial/` 按下表创建八篇文档。下列内容是写作问题，不是已完成结论；证据不足时解释缺口。每份正文包含 `## 证据与未确认项`。

| 文件 | 必须回答的问题 | 表达方式 |
|---|---|---|
| `INDEX.md` | 本轮分析范围、源码版本/工作区状态、完成程度、主要结论、未覆盖区域、阅读顺序 | 链接其余七篇；列出实际取证范围和预算使用 |
| `project-overview.md` | 谁使用、解决什么问题、核心能力、输入输出、技术栈、关键依赖、最小使用场景 | 功能—入口—模块—机制—证据状态表；注明示例是否运行 |
| `code-map.md` | 产品/包/目录怎样划分职责，入口与核心/支撑/集成代码在哪 | 模块—路径—职责—接口表，推荐阅读顺序 |
| `architecture.md` | 组件、部署/进程边界、外部系统、依赖方向与状态归属 | 至少一幅 Mermaid 架构图；实线为有依据的关系，虚线为推断 |
| `core-flows.md` | 代表性流程如何启动、经过哪些模块、数据怎样改变、怎样结束 | 至少一幅 Mermaid 流程/时序图；源码锚点；已知的失败边界 |
| `core-mechanisms.md` | 关键机制解决什么问题、原理是什么、实现在哪、为何有此取舍 | 每个机制按“问题→原理→实现→取舍→未解点”展开 |
| `design-highlights.md` | 值得学习的设计、适用条件、局限与创新证据 | 区分工程亮点、项目宣称、分析推断；无足够创新证据时直说 |
| `deep-dive-roadmap.md` | 下一轮研究什么、为何值得、从哪里开始、何时结束 | 稳定问题 ID，如 Q01；优先级、相关模块、已知证据、完成条件、状态 |

项目概览、机制和亮点可以交叉链接，避免重复介绍。仅架构与流程强制图表，不要求索引或路线图配图；不强制评分、固定洞察/陷阱数量、学习卡片。

## 状态记录

`analysis-state.json` 由准备器创建。执行时更新 `status`（`pending/in_progress/partial/complete`）、`sampled_files`（源码相对路径列表）、`usage`（`source_lines/rounds`）和 `unresolved`（未解问题字符串列表），保留 `source` 与 `budget` 原始基线。若源码中途变化，先记录影响并重新核对，不能仅替换 commit。

INDEX 的版本与状态应与记录一致。没有 Git 时 commit/dirty 指纹可为 null，需在 INDEX 说明证据有效性尚不能通过版本号判断。

> 从该项目的记忆系统中提炼的可移植原则

### 8.1 记忆设计原则

**原则1**: [原则名称]
- **原理**: [为什么重要]
- **证据**: [项目中的具体实现]
- **适用范围**: [什么场景适用]
- **去名检验**: ✅/⚠️

示例:
> **原则**: 记忆索引是有界上下文，详细内容应延迟加载
>
> **原理**: 索引在每轮对话中都会加载，成本固定；详细内容按需加载，成本可控。如果索引无界增长，每轮 token 消耗会失控。
>
> **证据**: 项目将 MEMORY.md 索引限制在 200 行/25KB，完整内容存放在独立 topic 文件中，Agent 按需 recall
>
> **适用范围**: 任何跨会话持久记忆系统
>
> **去名检验**: ✅ 通用原则

**原则2**: [同上格式]

示例:
> **原则**: 记忆应按类型分类，而非按时间排列
>
> **原理**: 类型分类支持系统性审计、修剪和提升；时间排列会退化为流水账，无法区分哪些值得保留。
>
> **证据**: 项目将自动记忆分为四类：user（用户身份）、feedback（行为纠正）、project（项目上下文）、reference（稳定事实）
>
> **去名检验**: ✅ 适用于所有知识管理系统

### 8.2 检索设计原则

**原则1**: [同上格式]

示例:
> **原则**: 可从代码/版本历史推导的内容不应存入记忆
>
> **原理**: 存储可推导内容浪费索引空间，且会在代码变更后过时。记忆应存储无法从当前上下文推导的信息。
>
> **证据**: 项目明确排除架构模式、代码风格等可从代码库推导的内容
>
> **去名检验**: ✅ 适用于所有缓存/记忆系统

## 9. ⚠️ 隐含陷阱

> 从源码分析中发现的非显而易见的记忆系统陷阱

### 9.1 存储陷阱

**陷阱1**: [陷阱名称]
- **现象**: [说明]
- **原因**: [说明]
- **正确做法**: [说明]

示例:
> **陷阱**: 索引截断是静默的，直到触发才报错
>
> **现象**: 新写入的记忆突然"消失"了，但没有任何错误提示
>
> **原因**: 索引有行数和字节数硬上限，超出后静默截断。长行条目（多句摘要而非一行钩子）可能在行数上限内就触及字节上限。
>
> **正确做法**: 索引条目保持一行（~150字符），详细内容放 topic 文件。定期清理过期条目。

### 9.2 并发陷阱

**陷阱1**: [同上格式]

示例:
> **陷阱**: 主 Agent 和后台提取 Agent 同时写记忆会冲突
>
> **现象**: 记忆内容被覆盖或产生重复条目
>
> **原因**: 两个写者同时操作同一个记忆存储
>
> **正确做法**: 实现互斥机制——如果主 Agent 在当前轮次写了记忆，后台提取器跳过该轮次

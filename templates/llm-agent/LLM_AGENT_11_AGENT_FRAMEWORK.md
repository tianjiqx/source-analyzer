# LLM Agent 框架依赖与集成分析

> 🔍 从项目依赖文件出发，识别项目使用的 Agent 框架和关键库，分析集成深度、抽象层设计、供应商锁定风险、迁移可行性

## ⚠️ 核心原则：从源码出发，未知则搜索

> **不要拿预设的框架列表去套项目。** 先读依赖文件，发现项目实际用了什么，再调用你的知识做分析。框架生态变化极快，任何写死的框架百科都会滞后——但分析方法论不会。

> **遇到不认识的库，必须主动搜索。** 用 `web_search` 或 `web_fetch` 查询库的文档、GitHub、README，补充背景后再分析。宁可多搜一次，也不要凭猜测下结论。

---

## 📋 分析流程

### Step 0: 依赖文件发现（必做，优先于一切）

**目标**: 从项目的依赖声明文件中，提取全部框架和关键库依赖。

```bash
# ─── Python ───
cat requirements.txt 2>/dev/null
cat pyproject.toml 2>/dev/null | grep -A200 'dependencies\|dev-dependencies'
cat setup.py 2>/dev/null | grep -i 'install_requires\|extras_require'
cat Pipfile 2>/dev/null | grep -A50 'packages\|dev-packages'
cat poetry.lock 2>/dev/null | head -500    # 精确版本

# ─── Java / Kotlin ───
cat pom.xml 2>/dev/null | grep -A3 '<dependency\|<artifactId\|<groupId'
cat build.gradle 2>/dev/null | grep -i 'implementation\|api\|compileOnly\|runtimeOnly'
cat build.gradle.kts 2>/dev/null | grep -i 'implementation\|api'

# ─── TypeScript / JavaScript ───
cat package.json 2>/dev/null | grep -A50 '"dependencies"\|"devDependencies"'
cat pnpm-lock.yaml 2>/dev/null | head -200  # 精确版本

# ─── C# / .NET ───
cat *.csproj 2>/dev/null | grep '<PackageReference'
cat Directory.Packages.props 2>/dev/null    # 中央包管理

# ─── Go ───
cat go.mod 2>/dev/null

# ─── Rust ───
cat Cargo.toml 2>/dev/null | grep -A50 '\[dependencies\]'
```

### Step 1: 依赖分类与框架识别

对每个依赖，先判断是否认识：
- **认识** → 直接进入分类和分析
- **不认识或不确定** → **立即搜索**（`web_search "<库名> <语言> library"`，或 `web_fetch` 读取其 GitHub/PyPI/npm 主页），补充以下信息后再分类：
  - 这个库是做什么的？
  - 在项目中扮演什么角色？
  - 是否是 Agent 框架或相关基础设施？
  - 社区活跃度（Stars、最近发布）？
  - 是否有已知的替代方案？

将所有依赖分为以下类别：

| 类别 | 说明 | 识别线索 |
|------|------|----------|
| **Agent 框架** | 提供 Agent/工作流/编排能力的核心框架 | 名称含 agent/graph/chain/crew/orchestrat |
| **LLM SDK** | 直接调用 LLM 的 SDK | openai/anthropic/google-generativeai/cohere |
| **LLM 统一层** | 多模型统一接口 | litellm/instructor/ports |
| **RAG / 向量库** | 检索增强相关 | faiss/chromadb/qdrant/pinecone/weaviate/milvus/llama-index |
| **工具 / 函数调用** | Tool/Function Calling 相关 | 名称含 tool/function/mcp |
| **可观测性** | 日志/追踪/监控 | langsmith/langfuse/weave/phoenix/opentelemetry |
| **Prompt 工程** | Prompt 模板/管理 | jinja2/promptflow/dspy |
| **基础设施** | Web 框架/任务队列/数据库 | fastapi/spring-boot/celery/redis |
| **其他关键库** | 不属于以上但重要的依赖 | 视项目而定 |

### 1. 框架识别与版本

#### 1.1 基本信息
- [ ] **框架名称与精确版本**

## 🔍 代码检查点

### 依赖文件快速扫描
```bash
# 自动检测所有已知依赖文件
for f in requirements.txt pyproject.toml setup.py Pipfile pom.xml build.gradle build.gradle.kts package.json *.csproj go.mod Cargo.toml; do
  if [ -f "$f" ]; then echo "=== Found: $f ==="; head -100 "$f"; echo; fi
done
```

### 框架 import 调用统计
```bash
# Python: 统计每个框架的 import 次数，找出核心依赖
grep -rh "^from \|^import " --include="*.py" . | sort | uniq -c | sort -rn | head -50

# Java: 统计包依赖
grep -rh "^import " --include="*.java" . | sort | uniq -c | sort -rn | head -50

# TypeScript: 统计 import
grep -rh "^import .* from " --include="*.ts" --include="*.tsx" . | sort | uniq -c | sort -rn | head -50
```

### 框架 API 调用密度
```bash
# 找出哪些模块框架耦合最深
# Python 示例
rg -l "from langgraph|from langchain|from crewai|from autogen|import spring_ai" --type py | while read f; do
  count=$(rg "from langgraph|from langchain|from crewai|from autogen|spring_ai" "$f" -c)
  echo "$count $f"
done | sort -rn | head -20
```

### 适配层检测
```bash
# 查找框架解耦模式
rg "class.*Adapter|class.*Facade|class.*Wrapper|class.*Provider|interface.*Provider" \
   --type py --type java --type ts --type cs -n
```

### 版本与更新检测
```bash
# 检查锁文件中的版本
cat poetry.lock 2>/dev/null | grep -A2 'name = '
cat pnpm-lock.yaml 2>/dev/null | grep 'version:'
cat package-lock.json 2>/dev/null | grep -A2 '"version"'
```

## 📊 评估标准

| 维度 | 优秀 (5分) | 良好 (4分) | 一般 (3分) | 需改进 (1-2分) |
|------|-----------|-----------|-----------|---------------|
| **框架选型合理性** | 选型有充分论证，匹配技术栈和需求 | 选型合理，但缺乏明确论证 | 选型可用但有更好的替代 | 选型不合理 |
| **集成架构质量** | 有适配层，业务逻辑与框架解耦 | 有一定抽象，但部分耦合 | 直接调用框架 API，耦合较深 | 完全绑定框架，难以替换 |
| **框架能力利用** | 充分利用核心能力，无重复造轮子 | 利用了主要能力 | 利用了部分能力，有重复造轮子 | 几乎没利用框架能力 |
| **供应商锁定风险** | 低锁定，易于迁移 | 有一定锁定，迁移成本可控 | 锁定较深，迁移成本高 | 深度锁定，几乎无法迁移 |
| **扩展与定制** | 合理扩展，遵循框架设计哲学 | 有扩展但不够深入 | 少量扩展 | 无扩展或过度修改框架核心 |
| **版本时效性** | 版本接近最新 | 略有滞后但无安全风险 | 版本较旧 | 版本严重过时或有安全漏洞 |

## 🔍 分析指引：框架知识的运用

> **关键**: 以下不是固定清单，而是分析时的**思考方向**。你应该基于自身知识对识别出的每个框架做这些分析。

### 识别框架的设计哲学

每个 Agent 框架都有核心设计理念，分析时应识别：
- **编排方式**: 显式状态机 vs 隐式 Chain vs Prompt 驱动 vs 可视化 DAG
- **抽象粒度**: 细粒度（节点/边）vs 粗粒度（Agent/Crew）vs 混合
- **类型安全**: 动态类型 vs 静态类型 vs 混合
- **运行模型**: 同步 vs 异步 vs 事件驱动 vs Actor 模型
- **扩展模式**: 继承 vs 组合 vs 装饰器 vs 插件 vs 配置

### 评估框架的适用边界

- 该框架的**甜蜜区**（sweet spot）是什么？
- 在什么场景下会**触碰天花板**？
- 该框架是否有**反模式**（官方不推荐但容易踩的坑）？

### 关注框架的生态系统

- 该框架属于哪个**更大的生态**？（如 LangGraph 属于 LangChain 生态）
- 它与其他框架/工具的**集成深度**如何？
- 它是**标准推动者**还是**标准跟随者**？（如 MCP 协议）

### 分析框架的演进风险

- 框架是否处于**活跃开发**中？（基于你的知识判断）
- 是否有**废弃信号**？（核心维护者离开、长时间无发布等）
- 是否面临**竞品替代压力**？
- API 稳定性如何？（频繁 Breaking Change 是风险信号）
- **如不确定 → 搜索确认**：`web_search "<框架名> latest release 2026"` 或 `web_fetch` 其 GitHub Releases 页

### 信息补充策略

> 分析中遇到知识盲区是正常的，关键是知道何时搜索、搜什么。

| 情况 | 行动 | 搜索示例 |
|------|------|----------|
| 完全不认识的库 | 搜索库名 + 语言 | `web_search "<库名> python library"` |
| 认识但不确定版本特性 | 搜索版本 + changelog | `web_search "<框架名> v2.0 changelog breaking changes"` |
| 不确定社区活跃度 | 搜索 GitHub 统计 | `web_fetch "https://github.com/<org>/<repo>"` |
| 不确定竞品 | 搜索替代方案 | `web_search "<框架名> alternatives <语言>"` |
| 不确定与竞品差异 | 搜索对比文章 | `web_search "<框架A> vs <框架B> comparison"` |
| 不确定生产案例 | 搜索 case study | `web_search "<框架名> production case study"` |

**原则**：
1. **先自身知识，后搜索** — 能确定的直接写，不确定的才搜
2. **搜索后标注来源** — "据 GitHub（2026-06 访问）" 而非断言
3. **搜索后更新认知** — 将新学到的框架知识应用到后续分析中
4. **宁搜勿猜** — 一个错误的框架描述比一个空的分析节更糟糕

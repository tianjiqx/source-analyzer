## 7. 💡 设计洞察

> 从该项目的缓存分层、请求合并与模型路由中提炼的可移植原则

### 7.1 缓存分层原则

**原则1**: 缓存应按成本和失效风险分层，而非单一缓存
- **原理**: 不同数据的变更频率和计算成本差异巨大；LLM 调用成本高但语义相似可缓存，工具结果成本低但可能实时变化，需要分层策略
- **证据**: 成熟实现区分语义缓存（embedding 相似度匹配，TTL 长）、结果缓存（精确匹配，TTL 短）、连接缓存（复用 HTTP 连接，无 TTL）
- **适用范围**: 所有需要平衡缓存命中率和数据新鲜度的 Agent 系统
- **去名检验**: ✅

**原则2**: 缓存键应基于语义相似度而非精确匹配
- **原理**: 用户提问的表述多样但语义可能相同，精确匹配缓存命中率极低，语义匹配可大幅提升命中
- **证据**: 实现中对用户输入做 embedding 后与缓存中的 embedding 计算余弦相似度，超过阈值（如 0.95）即命中
- **适用范围**: 问答类 Agent、重复率高的客服场景
- **去名检验**: ✅

### 7.2 模型路由与请求合并原则

**原则1**: 模型路由应基于任务复杂度动态决策，而非静态配置
- **原理**: 固定使用高端模型造成成本浪费，固定使用低端模型影响质量；应根据任务特征动态选择
- **证据**: 实现中先用小模型评估任务复杂度，简单任务路由到小模型，复杂任务路由到大模型；或根据工具调用数量、上下文长度等启发式规则路由
- **适用范围**: 多模型可用的 Agent 平台
- **去名检验**: ✅

**原则2**: 无依赖的工具调用应合并为并行批处理
- **原理**: Agent 规划中多个工具调用可能无数据依赖，串行执行浪费时间；合并为并行可显著降低总延迟
- **证据**: 实现中对工具调用做依赖图分析，无依赖的调用并行发出，结果聚合后继续推理
- **适用范围**: 多工具编排的 Agent 系统
- **去名检验**: ✅

## 8. ⚠️ 隐含陷阱

> 从源码分析中发现的非显而易见的性能优化陷阱

### 8.1 缓存一致性与并发限流陷阱

**陷阱1**: 语义缓存命中返回过期数据导致业务错误
- **现象**: 用户查询"今天的天气"命中了昨天的缓存，返回过期结果；或查询数据库状态命中缓存，返回已变更的旧数据
- **原因**: 语义缓存无法区分时间敏感查询和时效无关查询，统一使用 TTL 失效策略
- **正确做法**: 对时间敏感查询（包含"今天""当前""最新"等关键词）禁用语义缓存；对工具结果缓存设置短 TTL 并支持主动失效

**陷阱2**: 缓存击穿导致雪崩式 LLM 调用
- **现象**: 热门缓存项过期瞬间，大量并发请求同时穿透到 LLM API，导致成本飙升和延迟激增
- **原因**: 缓存过期时无互斥机制，多个请求同时发现缓存未命中并各自发起 LLM 调用
- **正确做法**: 使用 singleflight 模式——相同缓存键的并发请求只允许一个穿透到 LLM，其余等待结果；或采用缓存预热和随机 TTL 避免集中过期

### 8.2 冷启动延迟与并发限流陷阱

**陷阱1**: 模型路由的首次调用冷启动延迟被忽略
- **现象**: 动态模型路由在首次调用某模型时出现 5-10s 延迟（模型加载、连接建立、GPU 预热），用户感知到明显卡顿
- **原因**: 性能测试基于热缓存场景，未考虑冷启动延迟；模型路由未做预热
- **正确做法**: 系统启动时对常用模型做预热调用（warmup request）；连接池预建连接；本地模型预加载权重；冷启动时返回降级响应而非阻塞等待

**陷阱2**: 全局并发限流未区分优先级导致关键任务被阻塞
- **现象**: 高优先级用户请求被低优先级批处理任务占满的并发配额阻塞，导致 SLA 违约
- **原因**: 限流器采用全局统一配额，未按用户等级或任务类型分配独立配额
- **正确做法**: 实现分级限流——为关键路径（用户实时交互）和非关键路径（批处理、后台任务）分配独立配额；关键路径享有优先权和预留配额

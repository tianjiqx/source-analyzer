# LLM Agent 约束与权限系统分析

> 🔍 分析 Agent 的统一约束光谱：硬约束/软约束、执行点、优先级链、Fail-closed 设计
>
> **与旧版 06-Human + 07-Safety 的关系**: 本维度将两者统一为"约束系统"，覆盖从 Prompt 级软约束到代码级硬拦截的完整光谱

## 📋 核心问题清单

### 1. 约束光谱（Constraint Spectrum）

#### 1.1 约束硬度
- [ ] **硬约束（代码级，不可绕过）**
  - 工具调用前的参数校验？
  - 执行环境的沙箱隔离？
  - 输出过滤（正则/分类器）？
  - 资源限制（CPU/内存/网络/时间）？
  
- [ ] **软约束（Prompt 级，可被越狱）**
  - System Prompt 中的行为指令？
  - Few-shot 示例中的隐含规则？
  - 角色设定中的边界描述？
  
- [ ] **混合约束**
  - Prompt 声明 + 代码强制执行？
  - Prompt 建议 + 代码兜底？
  - 分级约束（低风险软约束，高风险硬约束）？

#### 1.2 约束表达
- [ ] **声明式约束**
  - 策略语言（CEL/Rego/YAML 规则）？
  - 规则引擎？
  - 配置文件定义？
  
- [ ] **命令式约束**
  - if-else 硬编码？
  - 装饰器/中间件？
  - AOP 切面？
  
- [ ] **混合表达**
  - 声明式为主 + 命令式兜底？
  - 策略引擎 + 自定义函数？

### 2. 约束执行点（Enforcement Points）

#### 2.1 执行阶段
- [ ] **Pre-execution（执行前）**
  - 输入验证（参数类型/范围/格式）？
  - 权限检查（是否有权执行此操作）？
  - 策略裁决（ALLOW/ASK/DENY）？
  - 风险评估（操作风险等级）？
  
- [ ] **During-execution（执行中）**
  - 资源监控（CPU/内存/时间）？
  - 进度检查（是否超时/死循环）？
  - 中间结果验证？
  
- [ ] **Post-execution（执行后）**
  - 输出过滤（敏感信息/格式校验）？
  - 结果验证（是否符合预期）？
  - 副作用审计（记录操作日志）？
  
- [ ] **Prompt-level（提示级）**
  - System Prompt 约束？
  - 工具描述中的限制说明？
  - 示例中的隐含规则？

#### 2.2 执行点编排
- [ ] **编排模式**
  - 串行检查（每个执行点依次检查）？
  - 并行检查（多个检查点同时执行）？
  - 短路检查（任一拒绝即终止）？
  
- [ ] **检查点配置**
  - 可配置启用/禁用？
  - 按工具/操作类型配置？
  - 按风险等级配置？

### 3. 策略引擎（Policy Engine）

#### 3.1 策略定义
- [ ] **策略格式**
  - 规则语言（CEL/Rego/自定义 DSL）？
  - YAML/JSON 规则？
  - 代码规则？
  
- [ ] **策略结构**
  - 条件（when）？
  - 动作（do: ALLOW/ASK/DENY）？
  - 优先级（priority）？
  - 原因（reason）？

- [ ] **策略示例**
  ```yaml
  # 示例策略
  - name: "no-delete-production"
    when: "tool == 'shell' && target.env == 'production' && action == 'delete'"
    do: DENY
    reason: "禁止在生产环境执行删除操作"
    
  - name: "ask-for-external-api"
    when: "tool.category == 'external_api'"
    do: ASK
    reason: "外部 API 调用需要用户确认"
  ```

#### 3.2 策略裁决
- [ ] **裁决类型**
  - ALLOW（允许执行）？
  - ASK（需要用户确认）？
  - DENY（拒绝执行）？
  
- [ ] **裁决逻辑**
  - 多策略匹配时的优先级？
  - 策略冲突解决（ALLOW vs DENY）？
  - 默认裁决（无匹配策略时）？

- [ ] **裁决解释**
  - 是否返回拒绝原因？
  - 是否返回匹配的策略？
  - 是否提供替代方案？

#### 3.3 策略管理
- [ ] **策略来源**
  - 内置策略（系统默认）？
  - 组织策略（管理员配置）？
  - 用户策略（用户自定义）？
  - 会话策略（运行时动态）？
  
- [ ] **策略优先级**
  - Platform > Org > User > Session？
  - 可覆盖？
  - 不可覆盖？

- [ ] **策略热更新**
  - 运行时加载新策略？
  - 无需重启？
  - 版本管理？

### 4. 权限模型（Permission Model）

#### 4.1 权限粒度
- [ ] **工具级权限**
  - 是否允许使用某工具？
  - 工具白名单/黑名单？
  
- [ ] **参数级权限**
  - 是否允许某参数值？
  - 参数范围限制？
  - 参数模式匹配？
  
- [ ] **资源级权限**
  - 是否允许访问某资源？
  - 文件路径限制？
  - 网络地址限制？
  
- [ ] **操作级权限**
  - 是否允许某操作类型？
  - 读/写/执行分离？

#### 4.2 权限决策
- [ ] **决策模式**
  - 白名单（默认拒绝）？
  - 黑名单（默认允许）？
  - 混合（部分白名单+部分黑名单）？
  
- [ ] **决策时机**
  - 调用前决策？
  - 运行时决策？
  - 延迟决策（先模拟再执行）？

- [ ] **决策缓存**
  - 相同请求缓存决策？
  - 缓存失效策略？
  - 缓存穿透？

#### 4.3 权限升级
- [ ] **升级机制**
  - 用户授权升级？
  - 时间窗口升级？
  - 范围限制升级？
  
- [ ] **升级约束**
  - 最大升级权限？
  - 升级审计？
  - 升级超时回收？

### 5. Fail-closed 设计

#### 5.1 故障模式
- [ ] **策略引擎故障**
  - 引擎崩溃时的默认行为？
  - 策略加载失败时的行为？
  - 策略解析错误时的行为？
  
- [ ] **权限服务故障**

- [ ] **约束检查故障**

#### 5.2 Fail-closed vs Fail-open

## 🔍 代码检查点

### 策略引擎
```bash
# 查找策略定义
rg "policy|rule|constraint|permission" --type py

# 查找 CEL/Rego
rg "cel|rego|policy_engine|rule_engine" --type py

# 查找裁决逻辑
rg "ALLOW|DENY|ASK|permit|forbid" --type py
```

### 权限检查
```bash
# 查找权限检查
rg "check_permission|can_execute|is_allowed|authorize" --type py

# 查找沙箱
rg "sandbox|isolation|restrict|limit" --type py
```

### Fail-closed
```bash
# 查找默认行为
rg "default_deny|default_allow|fail_closed|fail_open" --type py

# 查找降级
rg "fallback|degrade|emergency" --type py
```

## 📊 评估标准

| 维度 | 优秀 (5分) | 良好 (4分) | 一般 (3分) | 需改进 (1-2分) |
|------|-----------|-----------|-----------|---------------|
| **约束光谱** | 硬+软混合+分级 | 有硬约束 | 仅软约束 | 无约束 |
| **执行点** | 6+ 执行点全覆盖 | 3-5 个执行点 | 1-2 个执行点 | 无执行点 |
| **策略引擎** | 声明式+热更新+优先级 | 有策略引擎 | 硬编码规则 | 无策略 |
| **权限模型** | 细粒度+动态+审计 | 基本权限 | 粗粒度 | 无权限 |
| **Fail-closed** | 全面 Fail-closed | 部分 Fail-closed | Fail-open | 无考虑 |

```markdown
# [项目名] - 约束与权限系统分析

## 1. 约束光谱

**约束类型**:
| 约束 | 硬度 | 执行点 | 表达 |
|------|------|--------|------|
| 工具参数校验 | 硬 | Pre-execution | 代码 |
| 敏感操作审批 | 硬 | Pre-execution | 策略 |
| 行为边界 | 软 | Prompt-level | System Prompt |
| 输出过滤 | 硬 | Post-execution | 正则 |

## 2. 策略引擎

**策略格式**: CEL / YAML / 代码

**裁决类型**: ALLOW / ASK / DENY

**策略示例**:
```yaml
- name: "block-dangerous-shell"
  when: "tool == 'shell' && command matches 'rm -rf /'"
  do: DENY
  reason: "禁止危险命令"
```

## 3. 权限模型

**权限粒度**: 工具级 + 参数级 + 资源级

**默认策略**: Fail-closed（默认拒绝）

## 4. Fail-closed 设计

**故障模式**:
| 故障 | 默认行为 | 降级策略 |
|------|----------|----------|
| 策略引擎崩溃 | DENY | 记录日志，通知管理员 |
| 权限服务不可用 | DENY | 使用本地缓存 |
| 检查超时 | DENY | 记录超时，拒绝执行 |

## 5. 💡 设计洞察

### 原则1: 约束应该是分层的，不是扁平的
- **原理**: 不同风险的操作需要不同硬度的约束，一刀切要么过严要么过松
- **证据**: [项目实现]
- **去名检验**: ✅

### 原则2: Fail-closed 是安全系统的默认选择
- **原理**: 约束系统故障时，默认拒绝比默认允许更安全
- **证据**: [项目实现]
- **去名检验**: ✅

## 6. ⚠️ 隐含陷阱

### 陷阱1: 约束系统自身的攻击面
- **现象**: 攻击者通过构造特殊输入绕过约束检查
- **原因**: 约束检查器本身有 bug 或边界情况未处理
- **正确做法**: 约束检查器需要独立测试和审计，使用多层防御
```

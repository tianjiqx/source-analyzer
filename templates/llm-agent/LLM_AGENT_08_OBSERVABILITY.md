## 8. 💡 设计洞察

> 从该项目的分布式追踪、推理链可视化与成本归因中提炼的可移植原则

### 8.1 分布式追踪原则

**原则1**: 追踪 ID 应在请求入口生成并贯穿全链路
- **原理**: LLM Agent 调用涉及 LLM API、工具执行、记忆检索、子 Agent 等多个组件，没有统一的 trace ID 就无法关联同一请求的所有事件
- **证据**: 优秀实现在请求入口生成 UUID，通过 context propagation 传递到所有子调用，包括异步工具调用和子 Agent
- **适用范围**: 任何多组件协作的 Agent 系统
- **去名检验**: ✅

**原则2**: 推理链应作为一等公民记录，而非仅记录输入输出
- **原理**: Agent 的核心价值在推理过程，仅记录输入输出无法定位推理错误、幻觉来源和决策偏差
- **证据**: 成熟追踪系统记录每个推理步骤的 prompt、completion、tool selection rationale，支持推理树回放
- **适用范围**: ReAct/CoT 类 Agent、需要调试推理逻辑的场景
- **去名检验**: ✅

### 8.2 成本归因原则

**原则1**: 成本应归因到最细粒度的可追溯单元
- **原理**: 粗略的成本统计（如月度总费用）无法定位高成本任务、低效 Prompt 或异常消耗，需要按请求/步骤/工具粒度归因
- **证据**: 实现中每次 LLM 调用记录 model、input_tokens、output_tokens、cost，并关联到 request_id 和 task_id
- **适用范围**: 多租户 Agent 平台、需要成本优化的生产系统
- **去名检验**: ✅

**原则2**: 指标采样应保留异常值，避免平均化掩盖问题
- **原理**: 随机采样可能丢弃长尾延迟和异常成本事件，而这些恰恰是最需要诊断的问题
- **证据**: 优秀实现采用尾采样策略——正常请求低采样率，异常请求（超时、错误、高成本）100% 保留
- **适用范围**: 高流量 Agent 系统的监控采样策略
- **去名检验**: ✅

## 9. ⚠️ 隐含陷阱

> 从源码分析中发现的非显而易见的可观测性陷阱

### 9.1 日志敏感信息泄漏陷阱

**陷阱1**: Prompt 模板中嵌入的用户数据被完整记录到日志
- **现象**: 日志中包含完整的 system prompt + user message，其中可能包含用户的密码、身份证号、API Key 等
- **原因**: 日志记录层直接序列化请求对象，未在序列化前对敏感字段做脱敏
- **正确做法**: 实现日志脱敏中间件，对已知敏感模式（密钥前缀、PII 正则）自动替换为占位符；对 Prompt 中的变量区域做标记脱敏

**陷阱2**: 推理链日志暴露安全策略细节
- **现象**: 详细的推理链日志暴露了系统提示词中的安全规则、过滤逻辑和检测策略，攻击者可据此构造绕过方案
- **原因**: 调试日志未区分内部安全日志和可对外暴露的日志
- **正确做法**: 安全策略相关的推理步骤使用独立日志级别和存储，默认不对普通运维人员可见

### 9.2 追踪 ID 丢失与指标采样偏差陷阱

**陷阱1**: 异步工具调用中追踪上下文丢失
- **现象**: Agent 异步调用工具后，工具执行结果回调时无法关联到原始请求的 trace，导致追踪链断裂
- **原因**: 异步回调在新线程/进程中执行，context propagation 未跨越异步边界
- **正确做法**: 在发起异步调用时将 trace context 序列化传入回调；使用消息头传递追踪上下文；对跨进程调用使用 W3C Trace Context 标准

**陷阱2**: P99 指标在聚合时被平均化掩盖
- **现象**: 单请求 P99 延迟正常，但特定工具组合或特定模型路由的延迟异常被整体平均掩盖
- **原因**: 指标聚合维度不足，仅按接口聚合未按工具/模型/任务类型分维度
- **正确做法**: 按关键维度（模型、工具类型、任务复杂度）打标签，支持多维度下钻分析；设置分维度告警阈值

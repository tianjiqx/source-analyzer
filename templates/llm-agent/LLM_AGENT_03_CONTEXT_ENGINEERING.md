# LLM Agent 上下文工程分析

> 🔍 分析 Agent 的运行时上下文组装策略、Token 预算分配、压缩机制、信息注入时机
>
> **与 04-Memory 的区别**: Memory 关注"存什么、忘什么"（持久化）；本维度关注"每轮给 LLM 看什么"（运行时组装）

## 📋 核心问题清单

### 1. Context Assembly Pipeline（上下文组装管线）

#### 1.1 组装顺序与优先级
- [ ] **Slot 定义**
  - System Prompt 占位？
  - Memory/Recall 占位？
  - Tool Definitions 占位？
  - Conversation History 占位？
  - Tool Results 占位？
  - User Message 占位？
  
- [ ] **优先级链**
  - 哪些 Slot 是必保留的（不可压缩）？
  - 哪些 Slot 是弹性分配的？
  - 溢出时的裁剪顺序？

- [ ] **组装模式**
  - 静态模板（固定顺序+固定比例）？
  - 动态组装（根据任务类型调整比例）？
  - 自适应（根据实际 Token 消耗反馈调节）？

#### 1.2 Token Budget 分配
- [ ] **预算策略**
  - 静态分配（System 2K + Memory 1K + History 4K + Tools 2K）？
  - 动态分配（按需扩展，有上限无下限）？
  - 分层预留（硬预留 + 弹性池）？
  
- [ ] **预算计算**
  - Token 计数器实现（tiktoken/估算/精确）？
  - 不同模型的 Token 差异处理？
  - 输出 Token 预留？

- [ ] **溢出处理**
  - 硬截断（超过即报错）？
  - 智能裁剪（按优先级裁剪低优先级 Slot）？
  - 压缩降级（先压缩再截断）？

#### 1.3 信息注入时机
- [ ] **注入策略**
  - 每轮注入（System Prompt 每轮都发）？

  - 条件注入（满足条件时注入）？
  - 周期注入（每 N 轮重新注入）？
  
- [ ] **动态注入**

  - AFK Mode 注入（长时间无交互后首次注入状态）？
  - 上下文漂移纠正（检测到偏离时注入原始目标）？

### 2. Context Compression（上下文压缩）

#### 2.1 压缩层级
- [ ] **Level 0: 无压缩**
  - 全量保留所有消息？
  - 适用场景？
  
- [ ] **Level 1: Surgical Clearing（精准清理）**
  - 移除已消费的工具结果？
  - 移除中间推理步骤？
  - 保留最终结论？
  
- [ ] **Level 2: LLM Summarization（摘要压缩）**
  - 对历史消息做 LLM 摘要？
  - 摘要触发条件（Token 阈值/轮次阈值）？
  - 摘要质量保障？
  
- [ ] **Level 3: Truncation（硬截断）**
  - FIFO 截断（保留最近 N 条）？
  - 重要性加权截断？
  - 截断边界保护（不切断工具调用-结果对）？

#### 2.2 压缩触发
- [ ] **触发条件**
  - Token 达到阈值（如 80% context window）？
  - 消息数量达到阈值？
  - 定时触发（每 N 轮检查）？
  - 手动触发（用户命令压缩）？
  
- [ ] **渐进式 vs 一次性**
  - 渐进式（每轮微调）？
  - 一次性（达到阈值后大幅压缩）？
  - 混合（渐进清理 + 阈值触发摘要）？

#### 2.3 压缩质量保障
- [ ] **信息保留检查**
  - 压缩后是否保留关键决策？
  - 是否保留未完成任务的状态？
  - 是否保留用户偏好？
  
- [ ] **压缩验证**
  - 压缩前后的一致性检查？
  - 关键实体是否丢失？
  - 压缩质量评分？

**组装顺序**:
```
[System Prompt (必保留, ~2K)]
    ↓

    ↓
[Tool Definitions (弹性, ~2K)]
    ↓

    ↓

    ↓

```

**Token 预算分配**:
| Slot | 预留 | 弹性范围 | 溢出策略 |
|------|------|----------|----------|
| System | 2K | 不可压缩 | - |
| Memory | 1K | 0.5K-2K | 裁剪低相关性 |
| Tools | 2K | 1K-4K | 只保留相关工具 |
| History | 4K | 2K-8K | 压缩→截断 |
| Output | 4K | 不可压缩 | - |

## 2. Context Compression

**压缩层级**:
- Level 1: Surgical Clearing — 移除已消费的工具结果
- Level 2: LLM Summarization — 历史消息摘要（触发阈值: 70% window）
- Level 3: Truncation — 保留最近 20 条，不切断工具对

**压缩触发**: Token 达到 80% context window 时触发 Level 1→2→3

## 3. Dynamic Injection

**注入策略**:
| 注入内容 | 时机 | 格式 |
|----------|------|------|
| System Prompt | 每轮 | 内联 |
| Plan Reminder | 每 5 轮 | 标记注入 |
| Memory Recall | 按需 | 结构化 |
| Tool Results | 执行后 | 内联 |

## 4. Context Drift

**漂移检测**: 每 10 轮检查当前输出与原始目标的语义相似度
**纠正策略**: 相似度 < 0.6 时重新注入原始目标

## 6. 💡 设计洞察

### 原则1: 上下文是分层的，不是扁平的
- **原理**: 不同信息的重要性不同，扁平截断会丢失关键上下文
- **证据**: [项目实现]
- **去名检验**: ✅

### 原则2: 压缩应该是渐进的，不是突发的
- **原理**: 突发压缩导致信息断崖，渐进压缩保持连续性
- **证据**: [项目实现]
- **去名检验**: ✅

## 7. ⚠️ 隐含陷阱

### 陷阱1: 工具调用-结果对被截断
- **现象**: LLM 看到工具调用但没有结果，或看到结果但不知道是哪个工具的
- **原因**: 截断时没有保持工具调用-结果对的完整性
- **正确做法**: 截断边界检查，确保调用-结果对不被拆分

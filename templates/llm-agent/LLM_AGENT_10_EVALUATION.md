## 9. 💡 设计洞察

> 从该项目的评估基准选择、回归检测与 A/B 测试中提炼的可移植原则

### 9.1 评估基准选择原则

**原则1**: 评估基准应覆盖真实使用分布，而非仅追求标准基准高分
- **原理**: 标准基准（MMLU、HumanEval）衡量通用能力，但 Agent 的实际价值取决于特定场景表现；基准高分不等于生产好用
- **证据**: 优秀评估体系在标准基准之外构建领域特定的黄金数据集，按真实用户任务分布加权评分
- **适用范围**: 所有面向特定领域的 Agent 系统
- **去名检验**: ✅

**原则2**: 评估应分层进行——组件级→集成级→端到端级，逐层定位问题
- **原理**: 端到端评估能发现问题但无法定位根因；组件级评估可精确定位是哪个层（LLM/工具/记忆/规划）出了问题
- **证据**: 实现中先对 LLM 层做独立准确性测试，再对工具选择准确率测试，最后做端到端任务完成率测试
- **适用范围**: 多组件 Agent 架构的质量保障
- **去名检验**: ✅

### 9.2 回归检测与 A/B 测试原则

**原则1**: 每次变更都应执行回归评估，而非仅依赖 CI 单元测试
- **原理**: Agent 行为变更可能在单元测试中不可见（测试通过但输出质量下降），需要基于评估数据集的回归对比
- **证据**: 实现中维护黄金评估集，每次 PR 自动运行评估并与基线对比，质量下降超过阈值则阻断合并
- **适用范围**: 持续迭代的 Agent 系统
- **去名检验**: ✅

**原则2**: A/B 测试应以用户任务完成率为核心指标，而非模型输出相似度
- **原理**: 新 Prompt 或模型与旧版本的输出相似度低不代表质量差，相似度高也不代表质量好；只有用户任务完成率是真实信号
- **证据**: 实现中 A/B 测试分流真实用户流量，对比组的核心指标为任务完成率、用户满意度、重试率
- **适用范围**: 有真实用户流量的 Agent 系统
- **去名检验**: ✅

## 10. ⚠️ 隐含陷阱

> 从源码分析中发现的非显而易见的评估与测试陷阱

### 10.1 评估集污染与指标过拟合陷阱

**陷阱1**: 评估集被泄漏到训练或 Prompt 优化循环中
- **现象**: 评估得分持续上升但生产质量未改善，甚至下降；Agent 在评估集上表现完美但真实任务表现平庸
- **原因**: 开发者在 Prompt 迭代过程中反复参考评估集结果调整 Prompt，导致 Prompt 过拟合评估集；或评估集样本被意外包含在 RAG 知识库中
- **正确做法**: 评估集分为开发集（可调优）和测试集（严格隔离，仅最终验证使用）；定期更换测试集；对 RAG 知识库做评估集去重

**陷阱2**: 单一指标优化导致其他维度质量下降
- **现象**: 优化任务完成率后，成本上升 3 倍或延迟增加 5 倍；优化幻觉率后，任务完成率大幅下降
- **原因**: 仅优化单一指标，未考虑指标间的权衡关系；缺乏多目标帕累托最优意识
- **正确做法**: 定义多指标联合评估矩阵，设置各维度的最低可接受阈值；使用帕累托前沿分析选择最优配置

### 10.2 人工评估偏差陷阱

**陷阱1**: 评估者知道样本来源导致确认偏差
- **现象**: 评估者对"新版本"样本更宽容，对"旧版本"样本更苛刻，导致评估结果偏向新版本
- **原因**: 评估者知道样本的 A/B 分组，主观判断受期望影响
- **正确做法**: 实施盲评——评估者不知道样本来源；随机排列 A/B 样本；多名评估者独立打分取一致性

**陷阱2**: LLM-as-Judge 评估器与被评估模型同源导致评分膨胀
- **现象**: 使用 GPT-4 评估 GPT-4 的输出质量得到 90 分，但用户实际满意度仅 60 分
- **原因**: 同源模型倾向给风格相似、推理模式相似的输出更高分；评估 Prompt 中的评分标准被模型隐式迎合
- **正确做法**: 使用不同家族的模型做评估（如 Claude 评估 GPT 输出）；结合人工评估做校准；对 LLM-as-Judge 的评分做偏差校正

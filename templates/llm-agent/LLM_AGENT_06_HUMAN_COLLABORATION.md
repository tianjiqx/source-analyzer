## 9. 💡 设计洞察

> 从该项目的中断机制、信任边界与协作模式中提炼的可移植原则

### 9.1 中断点设计原则

**原则1**: 中断点应声明式配置而非硬编码
- **原理**: 声明式配置使中断点可按任务类型、风险等级动态调整，避免过度中断打断用户心流或中断不足导致失控
- **证据**: LangGraph 的 `interruptBefore`/`interruptAfter` 以节点粒度声明中断，支持运行时动态切换
- **适用范围**: 任何需要用户审批或多步任务可暂停恢复的 Agent 系统
- **去名检验**: ✅ 去掉具体框架名仍成立

**原则2**: 中断恢复必须保证幂等性
- **原理**: 用户可能多次暂停/恢复，或在中断后修改上下文；非幂等恢复会导致状态漂移或重复执行
- **证据**: 成熟 Agent 系统在 checkpoint 恢复时对比状态版本哈希，仅执行增量变更
- **适用范围**: 所有支持持久化状态和检查点恢复的 Agent
- **去名检验**: ✅

### 9.2 信任边界与渐进授权原则

**原则1**: 信任应渐进累积而非静态分配
- **原理**: 用户对 Agent 的信任随使用经验增长；初始过度授权引发安全事故，过度限制导致用户疲劳
- **证据**: 优秀系统记录用户历史审批/拒绝行为，自动调整同类操作的信任级别，减少重复确认
- **适用范围**: 长期运行的个人助手、自动化运维 Agent
- **去名检验**: ✅

**原则2**: 权限提升需要显式确认 + 时间/范围约束
- **原理**: 临时提权是高频场景（如执行危险命令），必须同时满足用户知情、时间窗口、操作范围三重约束
- **证据**: 实现中提权请求附带操作预览、倒计时自动回收、限定可操作资源范围
- **适用范围**: 涉及系统级操作的 Agent（DevOps、数据库管理）
- **去名检验**: ✅

## 10. ⚠️ 隐含陷阱

> 从源码分析中发现的非显而易见的人机协作陷阱

### 10.1 中断恢复竞态陷阱

**陷阱1**: 中断信号与状态保存之间的竞态条件
- **现象**: 用户发送中断时 Agent 正在执行工具调用，状态保存不完整，恢复后出现幽灵操作或部分执行
- **原因**: 中断处理与工具执行不在同一事务边界，中断信号到达时工具已部分完成但未记录
- **正确做法**: 在工具调用前设置 barrier，确保中断检查在工具执行前完成；使用补偿事务（Saga 模式）处理部分执行

**陷阱2**: 恢复时上下文已被用户修改导致不一致
- **现象**: 用户在中断期间修改了任务参数或环境配置，Agent 恢复后基于旧上下文继续执行产生错误结果
- **原因**: 恢复逻辑假设中断前后上下文不变，未检测上下文变更
- **正确做法**: 恢复时对比中断时和恢复时的上下文哈希，发现变更则重新规划而非直接恢复

### 10.2 权限提升攻击与用户疲劳陷阱

**陷阱1**: 权限提升请求被社会工程利用
- **现象**: 恶意构造的任务通过多步操作逐步获取高权限，最终执行超出用户预期的危险操作
- **原因**: 权限提升仅基于单步风险评估，未考虑多步操作的权限累积效应
- **正确做法**: 引入全局权限预算和累积风险评估，当连续操作的风险总和超过阈值时触发额外审批

**陷阱2**: 频繁确认导致用户疲劳后盲目批准
- **现象**: 系统对低风险操作也频繁弹出确认，用户习惯后对所有确认都点击"同意"，失去安全屏障意义
- **原因**: 确认粒度未根据风险等级区分，高确认频率导致"狼来了"效应
- **正确做法**: 仅对中高风险操作要求确认；低风险操作静默执行但记录审计日志；提供"信任此操作类型"选项减少重复确认

# 文件粒度深度分析模板

> **设计目标**: 实现从项目级 → 模块级 → 文件级的三层渐进式分析，每个关键文件都有独立分析文档。

---

## 分层分析策略

### 三层分析架构

| 层 | 产出 | 输出量 | 时间 |
|----|------|--------|------|
| **Layer 1** 项目级 (Project-Level) | 00-README.md (概览) · 01-architecture.md (架构) · INDEX.md (索引) | 3 文档 | 10-20 分钟 |
| **Layer 2** 模块级 (Module-Level) | 10-module-overview.md · 11-module-interface.md · 12-module-dependencies.md | 每模块 3 文档 | 每模块 10-15 分钟 |
| **Layer 3** 文件粒度 (File-Level) | 20-FileName-analysis.md（文件职责 · 关键函数/类 · 数据结构 · 依赖关系 · 设计模式 · 代码复杂度 · 改进建议） | 每关键文件 1 文档 | 每文件 5-10 分钟 |

### 选择分析深度

| 用户需求 | 分析深度 | 输出规模 | 适用场景 |
|----------|----------|----------|----------|
| "快速了解" | Layer 1 | 3 docs | 技术调研、选型对比 |
| "理解架构" | Layer 1+2 | 3+3N docs | 架构学习、设计借鉴 |
| "深度分析" | Layer 1+2+3 | 3+3N+M docs | 二次开发、深度学习 |
| "文件粒度分析" | Layer 3 (指定文件) | M docs | 针对性研究、代码审查 |

## 十二、💡 设计洞察 与 ⚠️ 隐含陷阱（必备蒸馏章节）

> **重要性**: 本文件级分析的**必备**章节，体现「提炼可移植原则」与「记录踩坑教训」的核心价值。
> 验证脚本（verify-analysis / review-agent）会检查这两个章节是否存在、数量是否达标（每条原则/陷阱）。缺失或不足会导致质量评分扣分。
>
> **标准标题格式**（必须）：
> - `## 💡 设计洞察`
> - `## ⚠️ 隐含陷阱`
>
> 兼容带编号变体（如 `## 12. 💡 设计洞察`），但推荐使用无编号标准格式。

### 12.1 💡 设计洞察（至少 2 条原则）

> 从该文件的实现中提炼**可移植**的设计原则——去掉本文件的具体名称后仍成立的通用做法。

每条原则用固定结构：

```markdown
**原则1**: [原则名称]
- **原理**: [为什么这个做法重要/有效]
- **证据**: [本文件中对应的具体实现，带 file:line]
- **适用范围**: [什么场景适用]
- **去名检验**: ✅ 通用 / ⚠️ 特定场景（说明去掉项目名后是否仍成立）
```

**原则2**: [同上格式]

示例:
> **原则1**: 用惰性迭代降低峰值内存
> - **原理**: 整条数据流在内存中物化会导致输入规模大时 OOM；惰性生成器让内存占用与输入解耦。
> - **证据**: `annotation.py:284` `_emit_docs_iter` 滑动窗口按需发射文档。
> - **适用范围**: 任何处理大体量输入的流式管线。
> - **去名检验**: ✅ 通用

### 12.2 ⚠️ 隐含陷阱（至少 2 条陷阱）

> 记录从源码中发现的**非显而易见**的实现陷阱——不读代码很难预见的坑。

每条陷阱用固定结构：

```markdown
**陷阱1**: [陷阱名称]
- **现象**: [出现什么问题]
- **原因**: [为什么会出现]
- **正确做法**: [应该怎么做]
```

**陷阱2**: [同上格式]

示例:
> **陷阱1**: `assert` 在 `-O` 优化下被移除
> - **现象**: 生产环境 `python -O` 运行时不变量检查全部失效。
> - **原因**: `assert` 是调试语句，`-O` 会剥离。
> - **正确做法**: 关键不变量用显式 `if ... raise` 而非 `assert`。

## 文件选择策略

### 自动识别关键文件

**优先级排序**:

1. **入口点** (权重: 10)
   - `main.*`, `Main.*`, `Application.*`, `Bootstrap.*`
   
2. **核心类** (权重: 9)
   - 文件名包含 `Service`, `Manager`, `Engine`, `Core`
   
3. **高频修改** (权重: 8)
   - Git log 最近 100 commits 修改最多的文件
   
4. **高复杂度** (权重: 7)
   - 圈复杂度 > 15 的文件
   
5. **接口定义** (权重: 6)
   - `Interface.*`, `API.*`, `Protocol.*`

### 文件数量控制

| 项目规模 | 分析文件数 | 选择策略 |
|----------|------------|----------|
| 小型 (<100 files) | 10-15 个 | 所有核心文件 |
| 中型 (100-500 files) | 15-30 个 | Top 20% 关键文件 |
| 大型 (>500 files) | 30-50 个 | 模块代表 + Top 10% |

### 命令示例

```bash
# 自动识别关键文件
python3 generate-file-list.py /path/to/project \
  --max-files 30 \
  --priority "entry,service,high-complexity"

# 手动指定文件列表
python3 generate-file-list.py /path/to/project \
  --files "Bootstrap.java,IndicesService.java,MemoryManager.java"
```

## 执行流程

### Step 1: 生成文件清单

```bash
python3 generate-file-list.py /path/to/project \
  -o $OUTPUT_BASE/project-name/FILE_LIST.md
```

**输出**:

```markdown
# [Project] File Analysis List

## Selected Files (30 files)

| 2 | IndicesService.java | service/IndicesService.java | P0 | 200 | service |
| 3 | MemoryManager.java | storage/MemoryManager.java | P1 | 180 | storage |
| ... | ... | ... | ... | ... | ... |

### Step 2: 创建任务管理

使用 `todo` skill:

```bash
todo add "文件粒度分析" --priority P0 --description "分析 30 个关键文件"

```
# 每 5-10 个文件一组，并行派发

# reading 图解项目

用于“图解项目”“用图系统理解核心原理”等请求。先遵循 [阅读整理指南](READING_SYNTHESIS.md) 的材料边界、预算和来源协议，再按本指南组织图解。普通整理仍按需配图，不自动生成整套图解路线。

## 以理解成果设计阅读路线

图解的目标是让读者解释项目如何工作、为什么这样设计、在哪些条件下成立，以及如何定位实现。先确定读者需要掌握的关键问题，再安排文章和图。目录、图数和模板是组织工具，不能以“填完几篇文章”作为理解完成的标准。

开始时从已有材料中提炼一段项目核心解释：**为了在什么约束下解决什么问题，项目采用了什么核心机制，因此获得什么能力，又付出什么代价。** 这一解释是后续取证与讲解的主线；有待确认的部分明确标注，不能先编一个故事再挑证据。

选择一条代表性场景贯穿全文，例如“一次查询从提交到结果返回”或“一次任务从创建到恢复”。建立关键概念的先修关系：只补充理解机制必需的背景，并链接已有解释，避免每页重复基础知识。静态架构、运行过程、状态/数据变化和设计取舍应围绕同一场景相互对应。

README 面向读者展示“先理解问题 → 建立全景 → 跟随执行 → 拆解核心机制 → 理解边界 → 定位实现”的路线；概览/专题/模块是存放与查阅方式，不是必须依次读完的课程。已有文章适用时直接复用；图解入口仅在能帮助导航时独立成页，不为目录完整而创建重复内容。

## 入口与范围

有已有底稿时进入 reading；没有底稿时，说明需要先取证，并按用户已授权的分析深度执行。仅请求图解且未指定深度时，先做有界初步分析，再整理材料支持的图解，不自动启动完整递归。只有仓库 README 或项目宣传信息时，将其作为文档声明，不能标为源码确认。

先在 `reading/PLAN.md` 记录读者、理解目标、核心问题、选定材料、阅读路线、取证缺口和本轮成本预算。3–5 张核心图只是小范围首轮参考，不是上下限；复杂项目可分多轮建立完整理解路径。输入与篇数采用 reading 的起始预算，按本轮目标与用户约束调整并记录原因；不能为了凑图扩写，也不能为了遵守建议篇数截断关键机制解释。硬性的用户预算优先，执行中不静默扩张；达到预算后保存可用成果，明确未完成的理解目标。

## 按问题选择图

| 阅读步骤 | 解释目标 | 推荐图形 | 建议位置 |
|---|---|---|---|
| 项目全景 | 用户、系统边界、外部依赖和主要能力 | 系统上下文图 | `overview/architecture.md` |
| 架构骨架 | 组件职责、分层、连接关系 | 架构图 | 同上，必要时拆页 |
| 典型执行 | 一次具体输入如何得到结果 | 时序图或数据流图 | `overview/execution-journey.md` |
| 核心原理 | 决定项目行为的关键机制如何工作 | 算法分步图、状态机或数据布局 | `topics/<mechanism>.md` |
| 设计取舍 | 机制为何这样设计，何时失效或受限 | 方案对比、失败路径图，表格清楚时用表格 | 同一专题或独立专题 |
| 模块实现 | 机制落在哪些模块和接口 | 局部结构图、接口时序图 | `modules/<module>.md` |

按项目选择核心机制：数据库可解释索引查找、查询执行或事务可见性；Agent 框架可解释执行循环、工具调用或上下文管理；编译器可解释中间表示与转换。不要把这些例子变成每个项目的必填清单。只有材料充分时才能描述异常恢复、并发语义或性能收益。

为每张图选择一个问题和抽象层级。大图难以跟随时，先用少量关键组件画总图，再拆局部机制图；同一组件在多页中保持一致名称。以同一个具体场景串联全景、执行和机制页，帮助读者将静态结构与运行行为对应起来。

## 核心机制要解释到什么程度

选择最能决定项目行为的机制，按以下问题建立因果解释；与项目无关的项目可以省略，关键缺口不能省略后标为已掌握：

1. **必要性：** 如果用一个直观的简单方案，会遇到什么具体问题或约束？
2. **表示：** 系统用什么核心对象、状态、索引或中间表示描述问题？对象的身份、所有权和生命周期在哪里确定？
3. **变化：** 从具体输入开始，逐步展示关键数据和状态如何改变，哪些条件决定分支与终止。必要时把一张静态图展开为若干前后状态快照。
4. **保证：** 机制要维持什么不变量，在哪个步骤维护，依赖哪些前提？区分设计预期与源码中实际存在的检查。
5. **代价：** 它怎样改善行为，又引入哪些资源消耗、复杂性或能力限制？没有测量时只解释有依据的成本结构，不编造收益数字。
6. **边界：** 改变一个关键条件（例如乱序、失败、取消、容量不足）后，行为如何改变？只选择与该机制有关且有证据支持的情形。
7. **落点：** 把概念映射到关键类型、函数和源码入口，给出下一步阅读顺序。不能把概念层的模块画成不存在的类。

用一份完整的 worked example 连接表示、变化和保证，展示必要的中间结果；只画函数调用框不足以解释算法原理。若简单替代方案并非项目真实实现，明确写“用于解释取舍的假设方案”。所谓项目精髓应落实为几条有适用条件的设计原则，说明何时可借鉴、何时不适用，避免泛泛罗列技术名词和“高性能、可扩展”。

## 图解单元

使用 [图解模板](../templates/reading/VISUAL_EXPLANATION.md)：问题 → 图示 → 按步骤读图 → 具体例子 → 取舍与边界 → 来源。图前说明适用版本、场景与抽象层级；图后解释关键箭头为什么成立、输入或状态怎样变化。

- 箭头标明调用、数据传递、依赖或状态转换，不能把 import 关系画成运行时调用。图例说明线型和颜色含义，颜色不作为唯一标记。
- 实现事实、概念示意和待确认推断分别用文字标注；教学假设输入和假设数值不能冒充项目实测。未知步骤不画成确定链路。
- 每个图解单元列出支撑关键节点与关系的底稿章节；必要时用“图中关系 → 底稿章节/源码锚点”小表映射，避免只列一串无法定位的来源。继承源码锚点时保留证据状态。
- 设计动机若仅为推断，标注为推断。没有作者材料支持时不代言作者；没有对照与测量时不声称原创性、领先性或性能增益。

## 图形格式与存放

默认用内嵌 Mermaid，便于审阅与增量修改。物理偏移、字节格式和内存布局用 ASCII，布局表达确有需要时可用 SVG。不要用绘图模型生成承担精确技术事实的图；若使用说明性插画，明确其为示意。

图形语法与样式按需查 [通用图表指南](DIAGRAM_GENERATION_GUIDE.md)，其中每篇必有图、直接读源码等完整分析要求不覆盖 reading 的阶段规则。源码锚点可以放图后映射表，避免长路径挤满节点。

默认图直接维护在所属正文内。需要分享或目标阅读器无法显示 Mermaid 时，可使用可用的渲染工具导出 SVG / PNG，存入 `reading/assets/<page-slug>/`，由正文相对引用并保留可编辑源。没有导出需求不生成图片副本。导出图与源图一起更新；来源登记在所属页面，资产不作为独立证据。现有 `--reading` 不校验图片内容或图片新鲜度，需在图解验收时检查。

## 阅读入口与来源追踪

需要独立图解入口时，在 `reading/overview/visual-guide.md` 写简短导读，以“读完能回答什么问题”的顺序链接各图所在文章/章节，不复制图及整篇解释。此页包含基于实际底稿的项目导读、适用版本与覆盖说明，也作为正文登记来源，不作为无来源导航豁免。尚未覆盖的问题直接说明，不建立空链接。

`reading/README.md` 展示理解路线，独立图解入口存在时链接该入口，并继续直接链接所有正文，满足现有验收协议。保持 overview → topics → modules 主目录，原递归底稿不改名、不迁移。

`sources.json.pages` 登记每篇图解页（含 `overview/visual-guide.md`）实际使用的底稿，图内与文字依据取并集；`materials` 使用真实指纹。页面间链接只是导航，不把其他 reading 页面作为证据。无需新增 schema 或 CLI 参数，沿用 `prepare-stage.py reading`。

底稿变化时，同步受影响正文、图、图例与导出文件；检查导读描述是否受影响。共享材料关联的页面全部修订后才更新公共指纹，未完成的页面在 README 标为待同步。缺失证据与冲突写入 `unresolved`；需要新取证的问题记录到深入路线/后续分析任务，不在纯整理中悄悄扫描源码。

## 理解缺口驱动的迭代

区分两种任务：用户仅要求整理已有材料时，缺口交付为待研究问题；用户要求读懂项目、掌握核心原理时，将定向补证纳入计划，按已授权范围衔接分析阶段。不要将“只能整理”当作整个学习任务的终点，也不要把学习目标扩大成全仓逐文件分析。

每轮走“提出核心问题 → 查阅底稿 → 找出影响解释的证据缺口 → 定向分析 → 更新底稿 → 修订图文 → 推演核对”。每个补证任务记录问题、已知入口、所需证据、预算、停止条件与受影响页面。新源码分析遵循主技能的图谱预检与证据规则，结论先写回合适的分析底稿（保留版本、路径/行号、证据状态），再登记为 reading 来源；不要让新的源码事实只存在于阅读页。历史底稿无需重跑整套初步分析，必要时新增有来源的专题底稿。

遇到版本冲突先解决具体冲突，不能通过更新指纹掩盖问题。无源码访问条件或超出用户授权范围时，将该理解目标标为未完成并给出可执行的后续取证入口。

## 用推演检查讲解是否有效

为关键机制安排少量有针对性的理解检查，可紧接正文或汇总在路线末尾：

- **复述：** 不看图，说明输入、关键状态变化、输出与约束。
- **推演：** 改变例子中的一个关键条件，预测哪条路径和哪些状态会变化。
- **解释：** 若去掉某个结构或步骤，会破坏哪个性质？
- **定位：** 想修改这一行为，应先读哪几个符号，又要检查哪些相邻机制？

给出参考推理与底稿依据，可放在折叠块或文末；与正文冲突时修正材料，而不是硬凑答案。此检查验证讲解是否支持推理，不声称用户已经掌握，也不强制生成另一套学习卡片。材料仅支持初步认识时，明确哪些问题尚不能回答。

## 验收与交付

1. 运行 `verify-analysis.py <分析根目录> --reading`，检查正文、导航、材料指纹和阶段状态。
2. 对本轮新增或修改、含 Mermaid 的正文运行 `mermaid-validator.py <页面路径>`。仅使用内置静态规则时，报告“静态检查”；有可用 mmdc 时可增加 `--use-mmdc`，按实际结果记录渲染验证。不要把规则扫描当作成功渲染。
3. 能预览时检查标签是否被截断、箭头是否混淆、图是否需要拆分。工具不可用时记录“未做渲染/视觉检查”，并保留图后的文字解释。
4. 逐图核对关键关系与底稿，确认时序、方向、状态变化、同步/异步与概念层级表达忠实；没有底稿依据的步骤删去或标为待确认。检查例子是否能沿图走到结果。
5. 按 PLAN 的理解目标逐项检查：是否能解释核心问题、走通具体例子、说明关键不变量和取舍、定位实现，并推演一个相关变化。缺少关键依据时保留未完成状态，不用其他图补足数量。交付 README 与实际创建的图解入口，说明覆盖的机制、材料深度和缺口。结构、静态语法、渲染、语义核对分别报告，不以图数或“能渲染”代替理解质量。

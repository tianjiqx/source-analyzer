# 原则蒸馏指南 (Principle Distillation Guide)

> **核心理念**: 代码是高维的，但有价值的设计模式是低秩的 — 蒸馏就是找到那些主成分。
>
> **目标**: 从"代码描述器"进化为"原则蒸馏器" — 不仅描述系统做了什么，更提炼读者能带走什么。

---

## 1. 什么是原则蒸馏

### 1.1 定义

**原则蒸馏**是在事实性分析基础上，提炼出**超越具体实现的可移植设计原则**的过程。

| 层次 | 输出 | 时效性 | 可移植性 |
|------|------|--------|----------|
| **事实性分析** | "这个项目用了 LRU 缓存" | 项目过时就没用 | 绑定具体代码 |
| **原则蒸馏** | "设计缓存时必须声明三要素：容量 + 淘汰 + 过期" | 长期有效 | 跨语言跨框架 |

### 1.2 为什么需要蒸馏

1. **信息 vs 知识**: 事实是信息，原则是知识。信息会过时，知识能复用。
2. **描述 vs 洞察**: 描述告诉你"它是什么"，洞察告诉你"我该怎么设计"。
3. **高维 vs 低秩**: 代码是高维的（百万行），但核心原则是低秩的（几条 Golden Rules）。

### 1.3 蒸馏的检验标准

**去名检验 (Name-Removal Test)**:

> 去掉项目名/语言/框架，这个原则还成立吗？

- ✅ **通过**: "缓存三要素必须显式声明" → 适用于任何缓存系统
- ⚠️ **部分通过**: "使用 React 做前端" → 实现细节，但"组件化设计"是原则
- ❌ **不通过**: "调用 XxxService.process() 方法" → 纯代码描述

## 2. 蒸馏的两个核心输出

### 2.1 Golden Rules (可移植设计原则)

**定义**: 从项目实现中提炼的、超越具体项目的设计原则。

**结构**:

```markdown
**原则**: [原则名称]

- **原理**: [为什么这个原则重要]
- **证据**: [项目中的具体实现]
- **适用范围**: [什么场景下适用]
- **去名检验**: ✅/⚠️ [去掉项目名后是否仍然成立]
```

**示例**:

```markdown
**原则**: 缓存三要素必须显式声明（容量 + 淘汰 + 过期）

- **原理**: 缺少任何一个都会导致问题 - 无容量→内存泄漏，无淘汰→热点堆积，无过期→脏数据
- **证据**: ClickHouse 的 mark-cache 配置了 max_cache_size，table-directories 配置了 ttl，query-cache 配置了 lru_policy
- **适用范围**: 任何缓存系统设计（Redis/浏览器/CDN）
- **去名检验**: ✅ 通用原则，适用于所有缓存场景
```

### 2.2 Gotchas (非显而易见的陷阱)

**定义**: 从源码分析中发现的隐性设计决策和潜在陷阱，违反会导致难以调试的问题。

**结构**:

```markdown
**陷阱**: [陷阱名称]

- **现象**: [如果做错了会看到什么]
- **原因**: [为什么会有这个陷阱]
- **正确做法**: [应该怎么做]
- **检测方法**: [如何发现这个问题]
```

**示例**:

```markdown
**陷阱**: 并发写入缓存时的竞态条件

- **现象**: 缓存中保留了旧值，新值被覆盖
- **原因**: 两个请求同时 cache miss，都去查数据库，后写入的覆盖先写入的
- **正确做法**: 使用 singleflight 模式，相同 key 只查一次数据库
- **检测方法**: 检查缓存写入路径是否有锁或原子操作
```

## 3. 蒸馏方法论

### 3.1 如何发现 Golden Rules

**方法 1: 从设计决策反推**

```
问题: 为什么项目选择了方案 A 而不是方案 B？
  ↓
分析: 方案 A 解决了什么问题？方案 B 有什么缺陷？
  ↓
提炼: 什么条件下应该选 A，什么条件下应该选 B？
  ↓
原则: "[条件] 下应该选择 [方案]"
```

**方法 2: 从问题-解决对反推**

```
问题: 项目解决了什么痛点？
  ↓
分析: 这个痛点的根因是什么？
  ↓
提炼: 这个根因在其他场景也会出现吗？
  ↓
原则: "当遇到 [痛点] 时，应该 [解决方案]"
```

**方法 3: 从权衡取舍反推**

```
问题: 项目在 X 和 Y 之间做了什么权衡？
  ↓
分析: 为什么选择了 X 而不是 Y？隐含假设是什么？
  ↓
提炼: 这个权衡在其他场景也成立吗？
  ↓
原则: "在 [假设] 下，优先选择 X；否则考虑 Y"
```

### 3.2 如何发现 Gotchas

**来源 1: 代码注释**

```bash
# 查找警告性注释
rg "WARNING|NOTE|HACK|FIXME|XXX|GOTCHA" --type py
rg "// 注意|// 警告|// 不要" --type py
```

**来源 2: 异常处理**

```bash
# 查找特殊异常分支
rg "except.*Exception|catch.*Error" -A 5 --type py
# 查找防御性检查
rg "if.*None|if.*empty|if.*invalid" --type py
```

**来源 3: 测试用例**

```bash
# 查找 edge case 测试（说明正常路径有隐含假设）
rg "test.*edge|test.*corner|test.*boundary" --type py
# 查找回归测试（说明曾经有 bug）
rg "test.*regression|test.*fix|test.*bug" --type py
```

**来源 4: 文档警告**

```bash
# 查找文档中的"不要这样做"
rg "do not|don't|never|avoid|beware" --type md -i
rg "不要|避免|注意|警告" --type md
```

**来源 5: 并发/竞态**

```bash
# 查找并发相关代码
rg "lock|mutex|atomic|race|concurrent|parallel" --type py
rg "thread.safe|synchronized|volatile" --type java
```

### 3.3 蒸馏的质量标准

| 维度 | 优秀 (5分) | 良好 (4分) | 一般 (3分) | 需改进 (1-2分) |
|------|-----------|-----------|-----------|---------------|
| **可移植性** | 去掉项目名完全成立 | 需要少量抽象 | 绑定特定技术栈 | 纯代码描述 |
| **实用性** | 直接指导设计决策 | 提供设计方向 | 需要二次解读 | 无法指导实践 |
| **深度** | 揭示隐性假设 | 揭示表面权衡 | 描述显式设计 | 描述实现细节 |
| **数量** | ≥5 条原则 + ≥3 条陷阱 | 3-4 条 + 2 条 | 1-2 条 + 1 条 | 无蒸馏内容 |

## 4. 蒸馏在分析流程中的位置

### 4.1 叠加在现有模板上

原则蒸馏**不替代**事实性分析，而是**叠加**在现有模板末尾：

```
现有模板结构:
├── 1. 目标场景
├── 2. 架构与原理
├── 3. 优缺点分析
├── 4. 竞品对比
├── 5. 架构决策记录(ADR)
├── 6. 性能瓶颈分析
├── 7. 参考文献
│
├── 8. 💡 设计洞察 (新增)      ← Golden Rules
│   ├── 8.1 核心设计原则
│   ├── 8.2 架构权衡决策
│   └── 8.3 性能优化模式
│
└── 9. ⚠️ 隐含陷阱 (新增)      ← Gotchas
    ├── 9.1 设计陷阱
    ├── 9.2 性能陷阱
    └── 9.3 扩展性陷阱
```

### 4.2 分析流程调整

```
Step 1: 事实性分析 (现有流程不变)
  ↓
  - 项目级分析: 架构、模块、数据流
  - 模块级分析: 接口、依赖、实现
  - 文件级分析: 类、函数、复杂度
  ↓
Step 2: 原则蒸馏 (新增步骤)
  ↓
  - 从设计决策中提炼 Golden Rules
  - 从异常处理/测试中发现 Gotchas
  - 对每条原则做"去名检验"
  ↓
Step 3: 输出完整文档
  ↓
  - 事实性分析 (原有章节)
  - 原则蒸馏 (新增章节)
```

## 5. 蒸馏示例

### 5.1 示例: 分析一个带缓存的数据库模块

#### 事实性分析 (现有输出)

```markdown
## CacheModule 分析

### 架构
- 使用 LRU 缓存策略
- 最大容量 1000 条
- 支持 TTL 过期

### 代码结构
- CacheManager 类：管理缓存生命周期
- CacheEntry 类：存储单条缓存
- EvictionPolicy 接口：淘汰策略

### 数据流
1. 查询时先检查缓存
2. 未命中则查数据库
3. 结果写入缓存
```

#### 原则蒸馏 (新增输出)

```markdown
## 💡 设计洞察

### 核心设计原则

**原则1**: 缓存三要素必须显式声明（容量 + 淘汰 + 过期）

- **原理**: 缺少任何一个都会导致问题 - 无容量→内存泄漏，无淘汰→热点堆积，无过期→脏数据
- **证据**: CacheManager 构造函数强制要求传入 max_size、eviction_policy、ttl 三个参数
- **适用范围**: 任何缓存系统设计（Redis/浏览器/CDN）
- **去名检验**: ✅ 通用原则，适用于所有缓存场景

**原则2**: 缓存失效比缓存写入更重要

- **原理**: 写入失败最多丢数据，失效失败会导致读到脏数据
- **证据**: CacheManager 的 invalidate() 方法使用了分布式锁，而 put() 方法只用了本地锁
- **适用范围**: 分布式缓存系统
- **去名检验**: ✅ 适用于任何分布式缓存

## ⚠️ 隐含陷阱

### 设计陷阱

**陷阱1**: 并发读写竞态

- **现象**: 缓存中保留了旧值，新值被覆盖
- **原因**: 两个请求同时 cache miss，都去查数据库，后写入的覆盖先写入的
- **正确做法**: 使用 singleflight 模式，相同 key 只查一次数据库
- **检测方法**: 检查缓存写入路径是否有锁或原子操作

**陷阱2**: TTL 过期检查是惰性的

- **现象**: 过期数据一直留在内存中，直到被访问
- **原因**: 为了性能，不在后台扫描过期数据，而是在查询时检查
- **正确做法**: 定期扫描 + 惰性检查结合，或者使用独立的过期清理线程
- **检测方法**: 监控缓存命中率、内存使用量、过期数据占比
```

## 6. 蒸馏检查清单

### 6.1 Golden Rules 检查

- [ ] 每条原则是否通过了"去名检验"？
- [ ] 每条原则是否有"原理"说明（为什么重要）？
- [ ] 每条原则是否有"证据"支撑（项目中的具体实现）？
- [ ] 每条原则是否有"适用范围"说明？
- [ ] 原则数量是否 ≥3 条？

### 6.2 Gotchas 检查

- [ ] 每条陷阱是否有"现象"描述（做错了会看到什么）？
- [ ] 每条陷阱是否有"原因"分析（为什么会有这个陷阱）？
- [ ] 每条陷阱是否有"正确做法"指导？
- [ ] 每条陷阱是否有"检测方法"说明？
- [ ] 陷阱数量是否 ≥2 条？

### 6.3 整体质量检查

- [ ] 蒸馏内容是否叠加在事实性分析之上（而非替代）？
- [ ] 蒸馏内容是否来自源码分析（而非泛泛而谈）？
- [ ] 蒸馏内容是否对读者有实际指导价值？

## 7. 常见错误

### 7.1 蒸馏不足

❌ **错误**: 只描述代码，不提炼原则

```markdown
# 错误示例
CacheManager 使用了 LRU 算法，最大容量 1000 条。
```

✅ **正确**: 从实现中提炼原则

```markdown
# 正确示例
**原则**: 缓存容量必须有硬上限
- **原理**: 无上限的缓存会导致内存泄漏
- **证据**: CacheManager 使用 max_size 参数强制限制容量
- **适用范围**: 任何缓存系统
```

### 7.2 原则不通过去名检验

❌ **错误**: 绑定具体实现

```markdown
# 错误示例
**原则**: 应该使用 Python 的 functools.lru_cache 装饰器
```

✅ **正确**: 抽象为通用原则

```markdown
# 正确示例
**原则**: 应该使用语言内置的缓存机制，而非手动实现
- **原理**: 内置机制经过充分测试，性能更优
- **证据**: Python 的 functools.lru_cache 是 C 实现的，比纯 Python 实现快 10 倍
- **适用范围**: 任何有内置缓存机制的语言
```

### 7.3 Gotchas 过于表面

❌ **错误**: 描述显而易见的问题

```markdown
# 错误示例
**陷阱**: 缓存未命中时需要查数据库
```

✅ **正确**: 揭示非显而易见的陷阱

```markdown
# 正确示例
**陷阱**: 并发写入缓存时的竞态条件
- **现象**: 缓存中保留了旧值
- **原因**: 两个请求同时 cache miss，后写入的覆盖先写入的
- **正确做法**: 使用 singleflight 模式
```
